## 2026-11-09 Phase 2 campaign decisions
- **Statuses:** SCHEDULED and AWAITING_CLOSURE were dropped; EMPLOYEE_SUMMARY_PUBLISHED will be a flag later. Launching moves DRAFT to INITIAL_MAPPING, the start date moves it to ACTIVE, and the day after the end date opens REVIEW_WINDOW (all calendar-driven, applied lazily on load and audited). Start date = start of diary observation; employees do Initial Mapping between launch and start.
- **Active-campaign slot:** INITIAL_MAPPING, ACTIVE and REVIEW_WINDOW occupy it. Enforced by a partial unique index plus a transactional check.
- **Eligible observation days are weekdays (Mon-Fri)** in the participant's range (campaign start or late join date, to end or stop date), minus absent dates. Public holidays are not modelled yet.
- **Campaign dates use the Europe/Tallinn calendar day.**
- **CampaignHistory table not created:** end-date changes (old, new, actor, time) are stored in AuditLog and shown to participants from there.
- **Reopen** goes LOCKED/FINAL to REVIEW_WINDOW, Organization Admin only, reason of 5+ characters, audited.
- **Retention snapshot** is a placeholder default (12 months, delete) until Phase 9 adds organization retention settings.
- **Not yet verified against a real database:** services in `src/lib/services/campaigns.ts` are only type-checked; their rules live in tested pure functions or DB constraints.

## 2026-11-10 Phase 2 correction: participant restoration
- **Participation periods.** New table `CampaignParticipationPeriod`: active over [startDate, inactiveFrom), with start kind (INITIAL, LATE_JOIN, RESTORED), who started it, and for closed periods the removal mode, who ended it and when. `CampaignParticipant.status` stays as the current state. Removal closes the open period; restoration opens a new one. Periods are never deleted, so the interruption and the original removal mode stay visible. A partial unique index allows only one open period per participant.
- **Effective date** of a removal or restoration is today (Europe/Tallinn), but never before the campaign start. The removal date is the first inactive day (matches: active 11-09 to 11-15, stopped 11-16, restored 11-20).
- **Inactive gaps** never count as expected diary days, missing logging days or coverage days. Coverage now takes a list of periods.
- **Final Analysis inclusion:** an EXCLUDED participant contributes nothing; after restoration their data inside active periods is eligible again; data dated inside an inactive gap is never eligible (`analysisPeriods`, `isActiveOn`).
- **Allowed states:** removal and restoration in INITIAL_MAPPING, ACTIVE and REVIEW_WINDOW; never once LOCKED or later (admin reopen applies). In a draft, removal still deletes the row (no data exists).
- **Who:** only the department's Department Manager (`campaign:manage`). The Organization Admin cannot manage participants; the admin's campaign role is create and reopen. Say so if you want the admin to restore participants too.
- **Confirmation:** stop, exclude, restore, cancel and lock now go through a confirmation page that shows the effective date; the server actions refuse to run without `confirmed=yes`.
- **Migration** backfills one period per existing participant (from joinedAt, closed at the removal date for stopped/excluded ones), so campaigns created before it keep their state.

## 2026-11-11 Phase 3 Initial Mapping decisions
- **Baseline versioning.** Each activity has versions. While the participant's mapping is a draft, version 1 is edited in place. Completing the mapping marks every version 1 as the baseline (`isBaseline`). After that an edit adds version N+1 and never touches the baseline. Activities added after completion start as non-baseline version 1. Draft activities can be deleted only before completion.
- **Mapping is prerequisite-gated.** Writing requires: own data, an active participation, About This Analysis acknowledged, and the campaign in INITIAL_MAPPING or ACTIVE (calendar-corrected). Managers see only the completion count ("X / Y"), not the activities.
- **Value category is not captured in Phase 3.** It is a later AI/manager-validated classification (a fixed list in code, not a table).
- **Frequency and occurrences.** `occurrenceCount` is per frequency period; for AD_HOC it is per month. Duration is 1-1440 minutes per occurrence. Phase 5 turns this into expected workload.
- **Reference data.** Categories, volume units and systems are per organization. Standard items load from `ensureStandardReferenceData` (seed, or the Organization Admin button "Load standard reference data"; idempotent). Admins can add categories (standard or department-specific), units and systems and deactivate them; deactivated items stay on existing activities. Category definition text is stored once (not per language) and feeds the guide now and AI later.
- **Systems are a managed list**, not free text, so later analysis can compare systems reliably.
- **Import.** Excel (.xlsx) and CSV through one library (`exceljs`). Template columns are fixed (no column guessing). Parsing is pure and reuses the same Zod schema as the form. The preview reports row-level errors and duplicate-name warnings; only rows without errors are imported, and the server re-validates every row on confirm (the client is not trusted). Limits: 1 MB, 200 rows.
- **Not verified on Railway yet:** the migration, the Excel upload through a server action (body size limit raised to 2 MB), and the client-side form state handling.

## 2026-11-12 Correction: user and department membership management
- **Correction 2 (participant restoration) was already delivered** in the Phase 2 correction (participation periods, Restore participant, confirmations, tests) and verified on Railway. It is unchanged here; this correction adds the user and membership management.
- **Users page** (`/admin/users`, Organization Admin only): create, view Active / Inactive / All, edit first name, last name and email, change department and role, deactivate and reactivate. Users have `firstName` and `lastName`; `name` stays as the display name, kept in sync by the service. The migration backfills first/last name for existing users by splitting at the first space. Organization Admin accounts are not created or deactivated here.
- **Membership history** reuses `DepartmentMembership` (`startedAt` / `endedAt` / `active` / `role`). Any change ends the current row and starts a new one; rows are never edited or deleted. A role change inside the same department is a new row too. The two partial unique indexes (one active membership per user, one active manager per department) are the backstop.
- **One service path.** Create, department change, role change, manager assignment and "add member" all go through one transactional function. It closes before it opens, so the unique indexes are never violated.
- **Managers.** Assigning a manager accepts any active non-admin user and moves them into the department if needed, which removes the old circular flow (a new department can get a manager without first having members). The previous manager stays in the department as an Employee. A department may be left without a manager (when its manager is moved or deactivated); the page shows "No manager assigned" and the audit entry carries `leftManagerVacancy`. There is no "remove from department" action: a non-admin must always have one department, so users are moved or deactivated.
- **Deactivation** ends the active membership, sets `active = false`, never deletes, and signs the user out (sessions are checked against the database on every request). Reactivation requires choosing a department and role and starts a new membership period; earlier history stays.
- **Campaign safety.** Moving or deactivating a user never touches `CampaignParticipant` rows. If the user is an active participant in a campaign that is not locked (draft, initial mapping, active, review window), the admin must tick an explicit acknowledgement, and the page lists the campaigns. The Department Manager then stops or excludes the participant using the normal participant rules. The audit entry records how many participations were left unchanged.
- **Default campaign participants** are active Employees with an active membership, so deactivated users are left out of new campaigns.
- **Audit actions added:** `user.created`, `user.updated` (field names only, no values), `user.departmentAssigned`, `user.departmentChanged`, `user.roleChanged`, `user.deactivated`, `user.reactivated`, `department.managerAssigned` (with previous manager). Participant stop and exclusion are the existing `campaign.participantRemoved` action with `metadata.mode`; restoration is `campaign.participantRestored`.
- **Department page** shows the manager and active member count, with "Manage members" and "Assign / Change manager" for the admin.
- **Not yet verified on Railway:** the migration (first/last name backfill) and the new pages.

## 2026-11-13 Membership UX and safety refinement
- **Two separate actions on the department page.** "Create new user" (a brand-new person; the department is preset and shown read-only, and the admin returns to the department page) and "Add / transfer existing user". They are different sections with different wording, so a transfer never looks like a plain add.
- **Existing-user chooser** is a searchable, grouped list: available users (no active department) first, then this department, then other departments alphabetically, each user labelled with their role. Selecting someone only shows their name, current department and current role. Inactive users and administrators are never candidates. Users already in the department are left out of the add/transfer list (their role is changed on their user page or via the manager picker).
- **Nothing changes on selection.** The chooser is a GET form that opens a confirmation page (`/admin/membership/confirm`), rendered as a page rather than a pop-up so it works without JavaScript and matches the other confirmations. It states: who is moving, from where, the effective date (today, Europe/Tallinn), that the old membership ends and is preserved, whether a previous manager becomes an Employee, and, for a transfer out of a department where the user takes part in a campaign that is not locked, the campaign warning with the campaign names and a required acknowledgement. Buttons: Cancel, and "Transfer employee" (or "Add to department" / "Make Department Manager").
- **One gated entry point.** `confirmMembershipAction` is the only way to add, transfer or re-role an existing user, and it refuses unless `confirmed=yes` (set only by the confirmation page). The Assign / Change manager picker and the department/role form on the user page use the same flow. The service still enforces the acknowledgement and never touches CampaignParticipant rows.
- **Return paths** are restricted to `/admin/...` paths (`safeReturnPath`).
- **Unchanged Correction 1 rules:** one active membership per user, history kept as ended and new rows, transfers audited (`user.departmentChanged` with from/to and the number of campaign participations left unchanged), deactivated users not candidates.

## 2026-11-14 Correction 3: organization privilege, department role and campaign participation
- **Actor model.** `Actor.role` (ADMIN | MANAGER | EMPLOYEE) was replaced by `isOrgAdmin` + `departmentRole` + `departmentId`. The earlier model treated the three as mutually exclusive: the session dropped the department of an admin and the services refused to give an admin a membership. The schema already separated the concepts, so no migration was needed.
- **Admins may hold a membership.** `applyMembership`, `reactivateUser` and the preview no longer reject Organization Admins; the candidate picker lists them like anyone else. Administrator accounts still cannot be deactivated from the Users page (lock-out safeguard) and there is still no UI to grant or revoke the privilege.
- **Default participants** are all active members of the department (manager included), not only Employees. `addParticipant` and `restoreParticipant` accept any active member. The error key `errNotDepartmentEmployee` now reads "not an active member".
- **Participant functions** (`campaign:acknowledge`, `mapping:write`, `diary:*`) are allowed for any department member for their own records in their own department. The services still require the user's own active CampaignParticipant row. The admin privilege alone grants none of them, and a membership in one department gives nothing in another.
- **Management functions** stay with the Department Manager of that department only. An admin who is not that department's manager cannot manage its campaign (they can create campaigns, reopen locked ones and administer the organization).
- **Reference data for participants.** In the participant views (mapping forms, template) even an admin sees only the standard items plus their own department's categories, matching what the server accepts.
- **Drafts** are visible to the department's manager and to admins. The participant area of the campaign page appears only when the viewer really is a participant.
- **Navigation** is grouped by capability (Organization / Management / My work) and shows "My campaign status" when the user takes part in a campaign.
- **Bug found by the new tests:** `createCampaign` passed the Department row (which has `id`, not `departmentId`) to the policy, so a Department Manager was refused creating a campaign for their own department; only admins could. It now passes `{ organizationId, departmentId }`.
- **Diary.** The Activity Diary is Phase 4. For now the policy actions `diary:write` and `diary:confirm` are defined and tested; tests of a manager actually creating diary entries or confirming a diary belong to Phase 4.
- **Self-review.** No new analysis or score about managers was added; see `authorization.md`.
- **Seed:** department Administration with Anna Admin (Organization Admin + Department Manager) and Kadri Mets (Employee). Run the seed (`SEED_ON_START=true`) or assign Anna a department on the Users page to try it.

## 2026-11-15 Phase 3 completion pass
- **Audit first, targeted changes only.** `phase-3-audit.md` lists what was complete, partial, missing, incorrect. Working code was kept; the migration is additive.
- **One canonical category, two languages.** Estonian definition/example columns were added to the existing record instead of creating Estonian business categories. Fallback to English per missing field. Existing standard categories are upgraded only when none of their Estonian fields were set.
- **Template language follows the interface language; the importer follows the file.** The template declares its version and language in a hidden `_meta` sheet (CSV: a first `#template_version=...;language=...` line). The importer reads either language's headings and labels, so an Estonian file can be imported while the UI is English; canonical values are identical.
- **Import policy.** Errors exclude a row, warnings need explicit acceptance (re-checked on the server), accepted rows are written in a single transaction, nothing is written before the confirmation step. A row with errors is never imported silently: the confirmation and result say how many were not saved. A file already imported (same content hash) cannot be imported again.
- **Idempotency.** The server issues a key at preview time; a unique `(participant, key)` makes a repeated confirmation return the existing result. The content hash blocks the same content under a new key.
- **No raw file retention.** The file is parsed in memory and dropped; only counts and a sanitized name are stored.
- **Plausibility warnings, not errors,** for a duration over 8 hours per occurrence or implausible occurrence counts per frequency.
- **Baseline identity.** On completion a hash of all first versions is stored with the participant: the input-data version a later analysis compares the diary against. It does not change when later refinements add versions.
- **Manager content view deferred.** The manager sees readiness only in Phase 3; content-level access comes with the analysis in Phase 5.
- **Demo data without an environment variable.** An admin button loads an idempotent synthetic department, campaign and mappings; it never adds a campaign to a department that already has one. `SEED_ON_START` is not needed.
- **Estonian labels** for frequency now read Igapäevane, Iganädalane, Igakuine, Kvartaalne, Aastane, Juhuslik.
- **Found while testing:** the Excel template formats dropdown cells in rows below the data, which made the old "row count" check count empty rows; the importer now bounds the sheet and counts only rows with content.

## 2026-11-16 Phase 4 Activity Diary decisions
- **Window rules.** Create: only while observation runs (ACTIVE), never in Initial Mapping or the Review Window; the date must be today or up to `retrospectiveWindowDays` calendar days back (so 3 allows today plus the 3 previous days), within the campaign, on a day the participant was actively participating (participation periods) and not marked absent. A stopped or excluded participant cannot add new entries. Review Window: edit existing entries and confirm; the date is fixed and deleting is not allowed. After locking, nothing changes.
- **Confirm My Diary** is a row per participant; any later correction withdraws it. Missing confirmations never block locking; the lock confirmation page shows how many are missing.
- **Timer** is stored on the server (a refresh or a closed tab does not lose it), one per participant, and is never stopped automatically. Stopping only ends the clock and opens the normal entry form with the duration to review and adjust; discarding saves nothing. Warnings (never a label): more than 3 times the mapped activity's duration (minimum 60 minutes) or more than 8 hours. The 8-hour maximum is a constant for now; the Organization Admin setting comes with the settings work.
- **Parallel work.** Overlapping explicit times are accepted. Recorded time is the sum of entered durations; "unique time" merges overlapping ranges (untimed entries are added as entered) and is shown only when an overlap exists. Out-of-scope time is shown separately.
- **Free-text activity vs mapped activity.** The participant chooses; a new activity is saved as described and is never merged. The AI hint ("this may belong to Bank Receipt Review") and the AI marker suggestion are Phase 6 (provider-independent AI layer) and are not implemented yet.
- **Shared meetings.** A participant defines a meeting once and adds it to their own diary; each other participant adds it to their own diary (one entry each, enforced by a unique index). Nobody writes into another person's diary.
- **Micro-activities** are consolidated entries using volume and unit ("8 cases, 35 minutes"); no per-action rows are required.
- **Reminders** are an in-app banner when the reminder time has passed and nothing is logged today; no Teams or email (interface for later).
- **Coverage for the manager** is "recorded on X of Y eligible days" per participant, ignoring absent days and inactive gaps; it is not a score or a percentage.
- **Audit.** Only diary confirmation is audited; individual entries are not (volume, and their content is private).
- **Favorites** are mapped activities only.
